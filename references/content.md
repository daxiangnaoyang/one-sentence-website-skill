# 内容契约与模板写入

网站内容要让访客理解“你是谁、解决什么问题、下一步怎么联系”。写入模板前先区分事实、推断和待补字段。`site.json` 是内容源；HTML 是构建产物，不直接改 `dist/`。

## 内容创建工作流

把“帮我写网站”拆成可审核的内容生产，而不是一次性生成整页文案。每轮只推进一个阶段，缺口保留为 `未获取` 或 `待用户确认`。

### 1. 采集一手材料

先收集用户已有材料，再写作。优先顺序是：用户口述或问卷、已有介绍文档、公开作品/项目链接、用户明确授权的图片，最后才是通用占位文案。首轮只问 1–3 个问题：

- 网站服务谁？访客看完后最希望做什么？
- 你提供的具体服务、作品或内容栏目是什么？有哪些明确不承诺的范围？
- 哪些姓名、照片、项目、数字、联系方式和外链允许公开？

不得根据域名、邮箱、社交账号或截图反推实名、资历、客户、收入和结果。登录状态不等于发布授权。

### 2. 生成内容 brief

先输出一页 brief，让用户审核方向，再写页面。至少包含：

```yaml
audience: 谁会访问
promise: 页面能清楚承诺的价值
primary_action: 一个主要行动入口
secondary_actions: 0-2 个次要入口
pages:
  - slug: home
    purpose: 首屏要回答的问题
    proof: 已有事实或链接
    missing: 未获取的信息
tone: 语气、禁用词和视觉关键词
publish_boundary: 允许公开与必须隐藏的字段
```

### 3. 按页面写作

推荐最小页面结构：

1. **首页**：一句定位、服务对象、核心结果、主要行动入口。
2. **关于/方法**：个人或团队是谁、如何工作、适合与不适合谁。
3. **作品/课程/服务**：每项说明对象、交付物、边界和下一步，不用空泛形容词替代证据。
4. **信任与证明**：只放可核实的项目、公开文章、截图或用户授权证言；没有材料就不生成“客户评价”。
5. **联系/报名**：明确入口类型和响应预期；静态页面不得伪造表单提交、付款成功或排队成功。

每个区块先写“访客问题”，再写 1 个结论、2–4 条证据或说明、1 个行动。首屏只保留一个主 CTA，其他入口降级为次要链接。

### 4. 事实与表达审校

把每条文案标记为 `fact`、`inference` 或 `missing`。以下内容必须逐条回到来源：数字、日期、客户名、收入、转化率、排名、认证、第一/唯一、效果保证和任何比较性结论。无法核验时删除、改为范围性描述，或明确写“待补充”，不得用 AI 补齐。

用户审核至少确认三件事：定位是否准确、公开边界是否正确、行动入口是否指向真实页面。审核意见先改 `site.json` 或 brief，再重新生成模板，不直接手改 `dist/`。

### 5. 图片、SEO 与 GEO 内容

- 图片只使用用户拥有发布权或明确授权的素材；为每张图记录用途、来源、替代文本和是否允许公开。
- `site.title`、`site.description`、Open Graph 文案、页面标题和 `sitemap.xml` 必须来自已审核定位，不能把关键词堆进正文。
- 结构化数据只填写已确认的姓名、组织、服务、页面和 URL；没有证据不生成评分、评论、资质或业务规模。
- 图片缺失时可先用明确标注的占位图做本地演示，生产检查前必须替换或移除。

### 6. 写入与复核

将审核后的内容写入 `site.json`，运行构建和生产检查，再人工打开 `dist/index.html` 检查首屏、链接、移动端布局、图片替代文本和隐私边界。内容创建完成的判据是：

- brief 与页面结构已确认；
- 公开字段都有来源或用户明确授权；
- 主 CTA、联系入口和外链可访问；
- 没有示例占位符、虚构证言、秘密或未授权素材；
- 用户已看过最终页面并确认可发布。

## 最小契约

```json
{
  "template": "profile|portfolio|service|creator",
  "site": { "title": "公开标题", "description": "可核实描述", "url": "https://example.invalid", "language": "zh-CN", "themeColor": "#f5f1e8", "demo": true },
  "person": { "name": "公开名称", "eyebrow": "身份标签", "role": "职责", "bio": "经确认的简介", "location": "城市或远程", "email": "公开邮箱", "avatar": "" },
  "links": { "primary": { "label": "发邮件", "url": "mailto:hello@example.invalid" }, "secondary": { "label": "了解更多", "url": "#about" } }
}
```

`site.demo` 必须是 boolean。四套模板内容只用于本地演示；上线前改为 `false`，替换 `example.com`、示例姓名、示例数据和“发布前替换”等标记。缺少真实材料时保留 `未获取` 在对话状态，不把它写成公开页面。

## 内容核对

- 名称、角色、简介由用户确认，不能从邮箱或域名猜实名。
- 只展示用户拥有发布权或明确授权的图片、文字、项目名和外链。
- 数字、客户名、收入、转化率、证言和“第一/唯一”需要来源；没有来源就删掉或标为待补。
- 邮件和电话只在用户明确要公开时写入。
- 静态模板可以链接邮件、电话、预约页或真实项目，不伪造表单提交成功、排队成功或客户反馈。

## 模板取舍

`profile` 强调身份卡与工作方式；`portfolio` 用项目网格组织作品；`service` 把服务边界、合作步骤和咨询入口放在前面；`creator` 以内容导航和栏目为主。会员、支付、数据库、后台编辑器和隐私同意记录不能由静态模板假装提供，先交付静态站，再拆动态扩展。

## 生产前内容门

```bash
node scripts/site.mjs build --project ./my-site
node scripts/site.mjs check --project ./my-site
```

不带 `--allow-demo` 时要求 `site.demo=false`，并检查演示占位符、危险链接、状态/凭据痕迹、缺失资源、viewport 和响应式 CSS。检查通过只证明脚本约束满足，仍需要用户看一遍页面并确认公开内容。
